# 2026-11-11 - rebuild phase 3: calculators (c1, c7, c3, c5, c2, c4, c6)

Branch `claude/rebuild-3-calculators`. Plan: docs/rebuild-plan.md (section 0 wins). Every
calculator page is a CalculatorPage over the shared profile; no hash or query is decoded, there is
no scenario layer, and legacy.ts exists for retirement and paycheck only (storage import). Existing

savingsRate.ts, contributionLimits.ts and paycheckSummary.ts and their tests.

## Semantics later slices rely on

- Retirement: the current plan is the scenario whose id starts with 'current-plan', else scenarios[0] (d1 replaces the 'Your Current Plan' name lookup in components/dashboard/derive.ts with `currentPlanScenario`). retirementHeadline(results, inputs, mode = 'today') ids: success, projected, required, withdrawal-rate; balances convert with displayDollars over (plan.retirementAge - startingAge) years; with no scenario the plan figures are null. Tones: success >= 0.7 positive, >= 0.5 caution, else negative; withdrawal <= 4% positive, <= 5% caution, else negative.
- Retirement filing status: marriedSeparate and headOfHousehold run as single, with the O10 note. The note is a ScreenNote on the retirement form's 'about' screen, and the collapsed card's summary says "<status>, run here as single", so it shows with or without results (it is no longer in the results column).
- Retirement basics: the retirement form asks the core facts its engine reads (no take-home pay, and no NET_PAY_AT_MOST_GROSS relation), with the old calculator's help on age, state and must-pay costs. Core screens of a calculator form show only on the calculator page (the intent intake asks CORE_FORM, then the form's non-core screens), so a form may override the help, hint and placeholder of its basics. test/lib/calculators/formBindings.test.ts checks that every field a calculator form asks is read by one of its bindings.
- Legacy import (lib/store/legacyImport.ts, lib/calculators/legacyImports.ts). D1, one call: `importLegacyStorage(LEGACY_IMPORTS)` imports every old key still in localStorage, in the fixed order of `LEGACY_IMPORTS` (the paycheck key first, then the retirement key; each entry is a `LegacyImport` of the calculator's legacy.ts and bindings.ts only), each key against the profile as the previous key left it, and removes each key after its import ran. useCalculatorBootstrap runs it on every calculator page (leverage and portfolio too, which have no old key of their own) once the profile store has hydrated and before the first submit, so the result no longer depends on which page a returning visitor opens first. A corrupt or foreign payload does not stop the other key, and nothing is read from it except the dollar display mode (D4: read from any old key whose envelope has `state.displayMode`, even when the rest of the payload is not a calculator payload). D2, one rule for every group of coupled paths (there is no pay rule of its own any more): (a) a key's writes are taken per group of coupled paths (`writeGroups`: groups that write a common path are merged; the paycheck income binding writes gross, take-home and frequency together, the Roth binding writes the 401(k) type, total and, for a split, the Roth part together) and a group is imported or skipped whole; (b) a group that differs from what the bindings write for the frozen old defaults is the visitor's own, imported and marked provided; (c) a group equal to the old defaults is imported unprovided, and only when an old default differs from the shared profile's default (`legacyDefaultGaps`; test/lib/store/legacyImport.test.ts pins the list: retirement age, invested balance, gross pay, monthly savings, must-pay costs; paycheck gross and take-home pay, state, 401(k) contribution 3% against 6%, emergency fund balance, must-pay costs, taxable contribution $0 against $500); (d) a provided path is never written, a group is skipped whole when one of its provided paths holds another value than the group would write, and an answered take-home pay must stay at most the gross pay (`keepsTakeHomeUnderGross`); (e) after each key, an unanswered take-home pay keeps the share of gross pay it had in its record (the key's own pay record when it has one, else the profile's before that key), written unprovided as min(round(share x gross, cents), gross) with the share capped at 1 (`takeHomeAtShare`); (f) the retirement binding writes a monthly, bi-weekly or semi-monthly salary as gross pay with that frequency, and a yearly or hourly salary as gross pay per paycheck of the frequency the profile holds at the same annual income, rounded to the cent (100,000 a year is 3,846.15 bi-weekly at the profile default). D3, accepted (not defects): for any path (pay, age, state, must-pay costs) both old keys changed to different values, the paycheck key's value wins because it is imported first, and the retirement key's value is dropped (paycheck age 31, retirement starting age 45 gives person.age 31). Both old keys hold the visitor's own pay: the paycheck record (gross, take-home, frequency) stays, and the retirement salary is dropped unless it writes the same values (yearly 100,800 next to 4,200 / 3,050 semi-monthly writes 4,200 and comes in as the same pay; yearly 120,000 is dropped). Only the retirement salary is the visitor's own: it is imported (the paycheck key's untouched defaults, if present, were written unprovided before it) and take-home pay keeps its share of gross (1,900 of 2,500 is 76%, so 120,000 a year gives 4,615.38 / 3,507.69 bi-weekly). Pay answered in the new site before any calculator was opened (the intake wizard does not run the import): an old pay group that conflicts with any answered pay path is skipped whole, not merged (only take-home pay answered: the old paycheck record is not imported; only the frequency answered: an old monthly salary in another frequency is not imported; only gross pay answered: an old paycheck record with another gross is not imported). Both keys untouched on pay: the later key's old default may replace the earlier one's, both unprovided (the retirement default 3,846.15 bi-weekly replaces the allocator's 2,500, take-home 2,923.07 at the allocator's 76%). Only take-home pay answered, and an old retirement salary with a frequency of its own (monthly, bi-weekly, semi-monthly; e.g. 8,000 monthly): accepted in this design as a consequence of the generic rule, and listed for the site owner in the pull request (not yet confirmed by the owner). The salary and its frequency are imported, the answered take-home number is kept as it is under the new frequency, and the import still refuses a salary below the answered take-home (I1 holds through keepsTakeHomeUnderGross). It is not reachable through the normal UI, because the wizard's pay screen marks gross, take-home and frequency together and every calculator page runs the import before any edit. D4: the dollar display mode is settled once per call from every old key present: a 'nominal' `state.displayMode` in any of them becomes the shared preference while that preference is still 'today' (the preference store writes its key on hydration, so the key cannot tell whether a mode was chosen); the old keys are no longer rewritten. test/lib/store/legacyImportInvariants.test.ts checks I1 to I6 over the payload grid (7 paycheck keys and none x 11 retirement keys and none) for five starting profiles (fresh, pay fully answered, only take-home, only frequency, only gross), and I7 on a sample by running the bootstrap of each of the four calculator pages. d1: the intake wizard and the dashboard do not run the import; d1 decides whether the dashboard should call `importLegacyStorage(LEGACY_IMPORTS)` too.
- Portfolio: choosing Custom after a preset writes portfolio.classTargets as that preset's weights (the visitor's own classes kept at 0%), in the calculator and in the wizard. Reducer ids also skip every id another row still refers to, so a new row never takes over a dangling reference.
- lib/profile/mappers.ts profileCompleteness (the deprecated v1 count used by the overview card, NextSteps, ContinueProfileCard and LearnChooser) counts investing.newCashThisMonth as answered once portfolio.accounts is answered: the deposits are the one record of the new cash. requiredSavingsCurve keeps the old semantics (target income not inflated; ages max(start + 10, 45) to 70; percent capped at 100).

## What a visitor sees differently

All calculators: generated input sections ask every field the engine uses; edits write through to
the profile; results recalculate live (no desktop Calculate button); invalid inputs keep the last
results under "Results out of date"; old share links and queries are stripped and ignored; each
intake lands on `<page>?from=profile`. On a narrow phone a section header's Restore defaults and
Show / Hide controls wrap onto two lines (FieldSection), so no calculator page scrolls sideways.

- Returning visitors (one-time import of the old keys, run by whichever calculator page opens first, with the same result on every page): the inputs and results match what the old calculator showed, including values left at an old default that differs from the profile's (for example the allocator's 401(k) at 3% and no taxable account). Where the two old calculators had different defaults for the same profile value (must-pay costs 4,000 against 2,500, gross pay) and the visitor told neither, the retirement key (imported second) wins. That holds for pay too: with both old keys untouched, the retirement import sets 100,000 a year (3,846.15 bi-weekly) after the allocator's 2,500 / 1,900, and the take-home pay keeps the allocator's share of gross pay (76%, so 2,923.07 bi-weekly). When both old keys hold the visitor's own pay, the allocator's paycheck record wins and a retirement salary of another income is dropped. A returning visitor with only the retirement key and a salary below the profile's yearly take-home pay (for example 50,000 a year) gets a take-home pay at the profile default share (1,428.57 of 1,923.08 bi-weekly), never one above gross pay.
- Shared dollar display (O15): retirement and paycheck read one preference ('bufo-preferences'). A future-dollars choice saved in either old calculator key is carried over once; the old per-calculator mode is otherwise gone.
- Retirement: income is the shared gross pay per paycheck and pay frequency (O11). The old hourly and yearly periods are gone (an old saved yearly or hourly amount, the untouched old default of 100,000 a year included, is imported as gross pay in the frequency the profile holds at the same annual income, e.g. 3,846.15 bi-weekly, and leaves the frequency alone); weekly pay enters the engine as a yearly amount (gross x 52), the other frequencies keep their period. Take-home pay is not asked on the retirement page. The basics keep the old help ("Your current age", "For state tax calculations", "Essential monthly expenses" plus the lookup hint); the healthcare multiplier's help reads "{x}x average cost" as the old readout did. Labels are the shared sentence-case ones (see the owner checks below).
- Retirement: inputs grow to savings, target, ss-healthcare and assumptions screens (effective tax rate and healthcare cost are auto/override fields; custom returns only for the custom profile); the O10 note. Results: the two header cards become StatTiles (same texts, no icons, tone tint); scenario details are a dl; chart captions move from above-right to a figcaption below each chart (same text); charts load lazily, do not animate, and use the theme mono font. Numbers are unchanged; a negative axis tick would read "-$5k" with U+2212 instead of "$-5000" (the series are not negative).
- Paycheck: inputs grow to the spending-bonus, emergency-fund, 401k, hsa, ira-taxable, debts and assumptions screens; O9 copy (fixed 22% federal bracket); four filing statuses (O10); no 300 ms delay. Results: bug 4, the HSA step card at 55+ reads "$0 of $9,750" (family) / "$0 of $5,400" (individual) instead of $8,750 / $4,400, and its per-paycheck amount includes the catch-up (for example $729 becomes $813 per monthly paycheck); every other figure is unchanged. The HSA note on the input card states the same limit (for example "$5,400/year limit: $450 per month" at 55 and over, individual; before: $4,400 and $367). The employer match limit is bounded 0-25% of pay (plan 2.3; the w1 intake allowed up to 100%): a saved value above 25% shows a field error and keeps the last results. The basics keep the old cards' help on age ("Used for catch-up contribution eligibility") and must-pay costs ("Rent, utilities, groceries, minimum debt payments, insurance, etc."), on the calculator page only. The debt-rate badge places the rate against the engine's 7% high-interest line ("High-interest (over 7%)" / "7% or less"); before it had three tiers at 8% and 5% with advice copy (a 7.9% loan moves from moderate to high; owner check below). The summary box footer loses its trailing colons; the paycheck flow is three StatTiles; the tier picker is a radio group (Basic / Intermediate / Advanced); quick-action cards are tinted in their urgency tone with outlined badges, and their buttons now scroll to the input section (they did nothing before); the progress bar is role=progressbar.
- Portfolio: /start/portfolio asks no basics (O5); the entry links that go through `coreStartLink('portfolio')` (home page, empty overview, NextSteps, IntentPicker) still start at /start (see deferred). With no saved data the page runs the profile's worked example instead of the old store seed: new cash $1,000 (Roth $0, Brokerage $1,000; before Roth $500, Brokerage $1,500, $2,000 in all) and targets 60/20/20/0 (before 60/25/15/0), so the cold-start trades differ. Switching the mix from a preset to Custom starts the editable targets from that preset. The intake checks custom targets with the engine's own rule (validateIntakeScreen runs classTargetsError from lib/calculators/portfolio/bindings.ts on the class-targets field), so a mix that does not total 100% stops Next with the calculator page's message. The overview card counts the new cash as answered once the accounts are.
