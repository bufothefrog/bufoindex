calculator page is a CalculatorPage over the shared profile; no hash or query is decoded, there is

## Semantics later slices rely on

- Retirement: the current plan is the scenario whose id starts with 'current-plan', else scenarios[0] (d1 replaces the 'Your Current Plan' name lookup in components/dashboard/derive.ts with `currentPlanScenario`). retirementHeadline(results, inputs, mode = 'today') ids: success, projected, required, withdrawal-rate; balances convert with displayDollars over (plan.retirementAge - startingAge) years; with no scenario the plan figures are null. Tones: success >= 0.7 positive, >= 0.5 caution, else negative; withdrawal <= 4% positive, <= 5% caution, else negative.
- Retirement filing status: marriedSeparate and headOfHousehold run as single, with the O10 note. The note is a ScreenNote on the retirement form's 'about' screen, and the collapsed card's summary says "<status>, run here as single", so it shows with or without results (it is no longer in the results column).
- Retirement basics: the retirement form asks the core facts its engine reads (no take-home pay, and no NET_PAY_AT_MOST_GROSS relation), with the old calculator's help on age, state and must-pay costs. Core screens of a calculator form show only on the calculator page (the intent intake asks CORE_FORM, then the form's non-core screens), so a form may override the help, hint and placeholder of its basics. test/lib/calculators/formBindings.test.ts checks that every field a calculator form asks is read by one of its bindings.
- Legacy import (lib/store/legacyImport.ts): writes are grouped per binding and groups that write a common path are merged, so coupled paths are compared and kept together. The paycheck income binding writes gross, net and frequency back together, and the Roth binding writes the 401(k) type, total and (for a split) the Roth part together. A group whose values differ from the frozen old defaults is the visitor's own and is imported as answers (marked provided). A group equal to the old defaults is still imported when one of those old defaults is not the shared profile's default (`legacyDefaultGaps`; test/lib/store/legacyImport.test.ts pins the list for each calculator: retirement age, invested balance, gross pay and frequency, monthly savings, must-pay costs; paycheck gross and take-home pay, state, 401(k) contribution 3% against 6%, emergency fund balance, must-pay costs, taxable contribution $0 against $500), so a returning visitor sees the inputs and results the old calculator showed them; these writes are not marked provided, so the intake still asks those questions and a later import of the other old key can still write them. A path already marked provided is never written; the rest of its group is imported only when every provided path in it already holds the value the group would write, and a group with a different answered value is skipped whole. One exception keeps the take-home pay: when the answered gross pay and frequency describe the same annual income as the paycheck key's own record (gross x paychecks per year, within one cent per paycheck of the more frequent pay), the paycheck key's gross, take-home pay and frequency are all imported, whichever key was imported first (the retirement key writes an old yearly or hourly amount as a monthly paycheck; weekly pay has no retirement period). When the annual incomes differ the whole pay group is still skipped, so the old take-home pay is lost rather than paired with a different gross pay. The retirement key's income group writes gross pay and frequency but no take-home pay: when it moves the pay frequency it also writes the take-home pay the profile holds (the profile default 2,600 bi-weekly, or an earlier paycheck import's), converted to the new frequency at the same annual amount and not marked provided (e.g. 2,600 bi-weekly becomes 5,633.33 a month), so a take-home amount never sits under another frequency's unit; when the take-home pay was answered, that group is skipped whole. The display mode is settled once, by the first import that meets an old key: a 'nominal' `state.displayMode` in any old key still present (LEGACY_DISPLAY_MODE_KEYS) becomes the shared preference while that preference is still 'today', and the mode is then removed from the other old keys, so their later import cannot undo a choice made in between (the preference store writes its key on hydration, so the key cannot tell whether a mode was chosen).
- Portfolio: choosing Custom after a preset writes portfolio.classTargets as that preset's weights (the visitor's own classes kept at 0%), in the calculator and in the wizard. Reducer ids also skip every id another row still refers to, so a new row never takes over a dangling reference.
- lib/profile/mappers.ts profileCompleteness (the deprecated v1 count used by the overview card, NextSteps, ContinueProfileCard and LearnChooser) counts investing.newCashThisMonth as answered once portfolio.accounts is answered: the deposits are the one record of the new cash. requiredSavingsCurve keeps the old semantics (target income not inflated; ages max(start + 10, 45) to 70; percent capped at 100).
- Paycheck: limits match optimization.ts (HIGH_INTEREST_THRESHOLD is exclusive, > 7%; HSA +$1,000 at 55; IRA +$1,100 at 50; 401(k) +$8,000 at 50 or +$11,250 at 60-63; 415(c) 72,000 / 80,000 / 83,250). paycheckSummary: deferrals and match are 0 without a plan; residualTaxes = max(0, gross - traditional - roth - net); effectiveRate = residual / (gross - traditional), 0 when that is <= 0. paycheckFlow: spending = monthlyToPaycheck(expenses + result.funMoneyAllocated); priority = net - spending and may be negative.
- Paycheck QuickActions scroll to `section[aria-label="<screen title>"]` from PAYCHECK_FORM; titles must stay unique. Below lg with the Results tab open the inputs column is hidden, so the button does nothing visible there (as before the rebuild).
- Portfolio: portfolioHeadline(result) ids invested, cash-leftover, drift-before, drift-after (only drift-after has a tone, brand). Drift lines are signed '+' only when positive and print an ASCII '-'; sell amounts keep an ASCII '-' prefix. Only portfolio-level drift rows (accountId null) are shown. Test ids kept: tax-event-warning, account-plan-<id>, plan-row-<holdingId>, class-drift-table, drift-row-portfolio-<class>, placement-advice-*.
- Leverage: debounce 250 ms; contribution, years and starting balance are nullable overrides derived from the profile; the ratio and overrides persist through the profile.
- Results render from the inputs snapshot; `stale` is in each results props type but not read (the shell marks stale results).

## What a visitor sees differently

All calculators: generated input sections ask every field the engine uses; edits write through to
the profile; results recalculate live (no desktop Calculate button); invalid inputs keep the last
results under "Results out of date"; old share links and queries are stripped and ignored; each
intake lands on `<page>?from=profile`. On a narrow phone a section header's Restore defaults and
Show / Hide controls wrap onto two lines (FieldSection), so no calculator page scrolls sideways.

- Returning visitors (one-time import of the old keys): the inputs and results match what the old calculator showed, including values left at an old default that differs from the profile's (for example the allocator's 401(k) at 3% and no taxable account). Where the two old calculators had different defaults for the same profile value (must-pay costs 4,000 against 2,500, gross pay), the calculator imported last wins for values neither one was told. That holds for pay too: with both old keys untouched and the paycheck key imported first, the retirement import then sets 100,000 a year (8,333.33 a month) and the allocator's old take-home pay (1,900 bi-weekly) is kept as the same annual amount a month (4,116.67), so the allocator then runs on that pay, not on the old store's 2,500 bi-weekly.
- Shared dollar display (O15): retirement and paycheck read one preference ('bufo-preferences'). A future-dollars choice saved in either old calculator key is carried over once; the old per-calculator mode is otherwise gone.
- Retirement: income is the shared gross pay per paycheck and pay frequency (O11). The old hourly and yearly periods are gone (an old saved yearly or hourly amount, the untouched old default of 100,000 a year included, is imported as a monthly paycheck of the same annual income, e.g. 8,333.33 a month); weekly pay enters the engine as a yearly amount (gross x 52), the other frequencies keep their period. Take-home pay is not asked on the retirement page. The basics keep the old help ("Your current age", "For state tax calculations", "Essential monthly expenses" plus the lookup hint); the healthcare multiplier's help reads "{x}x average cost" as the old readout did. Labels are the shared sentence-case ones (see the owner checks below).
- Retirement: inputs grow to savings, target, ss-healthcare and assumptions screens (effective tax rate and healthcare cost are auto/override fields; custom returns only for the custom profile); the O10 note. Results: the two header cards become StatTiles (same texts, no icons, tone tint); scenario details are a dl; chart captions move from above-right to a figcaption below each chart (same text); charts load lazily, do not animate, and use the theme mono font. Numbers are unchanged; a negative axis tick would read "-$5k" with U+2212 instead of "$-5000" (the series are not negative).
- Paycheck: inputs grow to the spending-bonus, emergency-fund, 401k, hsa, ira-taxable, debts and assumptions screens; O9 copy (fixed 22% federal bracket); four filing statuses (O10); no 300 ms delay. Results: bug 4, the HSA step card at 55+ reads "$0 of $9,750" (family) / "$0 of $5,400" (individual) instead of $8,750 / $4,400, and its per-paycheck amount includes the catch-up (for example $729 becomes $813 per monthly paycheck); every other figure is unchanged. The HSA note on the input card states the same limit (for example "$5,400/year limit: $450 per month" at 55 and over, individual; before: $4,400 and $367). The employer match limit is bounded 0-25% of pay (plan 2.3; the w1 intake allowed up to 100%): a saved value above 25% shows a field error and keeps the last results. The basics keep the old cards' help on age ("Used for catch-up contribution eligibility") and must-pay costs ("Rent, utilities, groceries, minimum debt payments, insurance, etc."), on the calculator page only. The debt-rate badge places the rate against the engine's 7% high-interest line ("High-interest (over 7%)" / "7% or less"); before it had three tiers at 8% and 5% with advice copy (a 7.9% loan moves from moderate to high; owner check below). The summary box footer loses its trailing colons; the paycheck flow is three StatTiles; the tier picker is a radio group (Basic / Intermediate / Advanced); quick-action cards are tinted in their urgency tone with outlined badges, and their buttons now scroll to the input section (they did nothing before); the progress bar is role=progressbar.
- Portfolio: /start/portfolio asks no basics (O5); the entry links that go through `coreStartLink('portfolio')` (home page, empty overview, NextSteps, IntentPicker) still start at /start (see deferred). With no saved data the page runs the profile's worked example instead of the old store seed: new cash $1,000 (Roth $0, Brokerage $1,000; before Roth $500, Brokerage $1,500, $2,000 in all) and targets 60/20/20/0 (before 60/25/15/0), so the cold-start trades differ. Switching the mix from a preset to Custom starts the editable targets from that preset. The intake checks custom targets with the engine's own rule (validateIntakeScreen runs classTargetsError from lib/calculators/portfolio/bindings.ts on the class-targets field), so a mix that does not total 100% stops Next with the calculator page's message. The overview card counts the new cash as answered once the accounts are.
- Portfolio: the share hash is no longer written; a non-Latin-1 account name survives a reload (bug 2); removing an account asks first. Results: cash and drift figures are StatTiles (same text, "3.0%" kept through 'percent-1'); tables are DataTables with captions and row headers, no font-mono and no CSS uppercase headers; the tax warning is a tinted StatusAlert; "on target" uses text-sage-700 in light mode.
- Leverage: the third headline tile is labelled "Share of simulated paths where the {L} fund ends behind the index fund" above its value (before: the value, then "of simulated paths where the {L} fund ends behind the index fund"); the other labels and every figure are unchanged. The headline tiles are a polite live region, so a recalculation is announced (the old wrapper announced the whole results).
- Leverage: the c/y/b/l query is stripped and ignored; the ratio and overrides survive a reload (bug 5); the form adds the leverage ratio and Restore defaults on market assumptions; results use StatGrid, DataTable, KeyValueList and a lazy chart.
